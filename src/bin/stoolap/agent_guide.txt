Stoolap agent mode: SQL in, one JSON line per statement out.

RUN
  stoolap --agent -e "SELECT 1 AS a; SELECT nope"
  stoolap --agent -f script.sql            (or SQL on standard input)
  stoolap --agent -d file:///path/to/db -f script.sql    (default -d memory://)

OUTPUT (standard output holds nothing else)
  {"stoolap":"0.5.1","commit":"...","build":"release","features":[...],"dsn":"memory://"}
  {"stmt":1,"line":1,"ok":true,"columns":["a"],"types":["INTEGER"],"rows":[[1]],"row_count":1,"hash":"ff4ea0efc5072510","order":"unordered"}
  {"stmt":2,"line":1,"ok":false,"error":{"kind":"column_not_found","message":"column 'nope' not found"}}
  {"done":true,"statements":2,"failed":1,"first_failed":2,"open_transaction":false}

  The first line names the build: times mean something only from "build":"release".
  A write gives "rows_affected" (an upsert counts the rows it wrote), EXPLAIN gives
  "plan" as an array of its lines, a failure gives "error" with a "kind" such as
  parse, table_not_found, unique_constraint or query_cancelled; a timeout adds
  "timeout_ms". "rows" holds the first 40 rows (-l N, -l 0 for all, --no-rows
  none); "row_count" counts every row.
  Exit status: 0 all passed, 1 a statement failed, 2 bad arguments.

COMPARE ANSWERS
  "hash" covers every row, values and types. The same hash from two builds or two
  runs is the same answer. "order":"ordered" (an ORDER BY outside parentheses)
  means the hash follows the rows' order; otherwise the order does not change it.

MEASURE
  --timing              adds "elapsed_us": the engine's time for the statement, its
                        parse, plan and every row, without writing the output
  --no-rows             leaves the rows out: row_count, types, hash and times stay
  --repeat N            runs each statement that only reads N times in the process
  --warmup M            adds M unmeasured runs after the first
  The line adds "repeat":{"runs","warmup","first_us","min_us","p50_us","p90_us",
  "max_us"}: first_us is the cold run, the rest the warm ones; with --timing,
  elapsed_us is the cold run too. A statement that is not repeated says why:
  "repeat":{"runs":1,"skipped":"not_read_only"} for a write, "explain" for EXPLAIN.
  The gap between first_us and p50_us is the cold parse, plan and caches.
  Times are microseconds to the nanosecond: 7.625.

PARAMETERS
  SELECT * FROM t WHERE id = $1 AND name = $2; -- PARAMS: 42, 'alice'
  On the statement's line or the line before. The values are SQL literals, read
  as SELECT reads them: text in single quotes ('it''s', 'a, b'), -5, 1.5, TRUE,
  NULL, DATE '2024-01-02'. Anything else, a word, a function or a second
  statement, fails the statement with kind "params" and does not run.

SCENARIOS
  A line "-- @case <name>" starts a case: the statements after it run in a fresh
  in-memory database and their lines carry "case". The summary adds "cases".

COMMANDS (a line between statements)
  .schema [table]       every table's CREATE TABLE, indexes and row count, and views
  .stats                memory, volume and index statistics

DEFAULTS
  -t MS                 statement timeout; 30000 in agent mode, -t 0 for none
  --on-error stop       stop at the first failure (default continue)
  --full                keep text cells over 1,000 characters whole
  STOOLAP_AGENT=1 turns agent mode on, --no-agent off. Pipes never turn it on.
